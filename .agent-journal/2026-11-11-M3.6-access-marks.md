# 2026-11-11 — M3.6 — Access marks on types

Role: system designer and architect (after a sparring session on RBAC). Task: M3.6, one frozen part.

## Decisions with Tomas

- Required privilege lives on the type as a mark, not in an api table. Reason: a third-party type gets a safe default without any api knowing it; Matter does the same (requirement in the cluster spec, grants in the ACL).
- An api uses the marks only if it wishes. Home API: as written, no override. WS API: open — leaning yes, client profiles may only ask for more (Inspector: `administer` everywhere). Matter bridge: own ACL.
- `Privilege` = `view < operate < manage < administer` (Matter-style, ordered).
- Marks in one dictionary `access`, typed per shape: reading `read`; channel `read`/`write`/`proof`; method `call`/`proof`. Defaults from shape and `effect`. Name `access`, not `auth` (authn/authz mix) or `security` (overlaps 03a `sensitive`).
- `proof` moves into `access`. `level` is not a mark: it belongs to the session and stays 13a policy.
