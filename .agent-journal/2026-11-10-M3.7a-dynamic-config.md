# 2026-11-10 — M3.7a — Main driver, dynamic config and bootstrap

Role: system designer and architect. Task: M3.7a (new, added this session).

## Decisions with Tomas

- Config can be written from the UI; a static-only config stays possible. Reason: goals promise configuration without CLI; 16 had it open.
- Config ≠ user data stays: home devices, settings, aliases remain in KV. Reason: the EVOK lesson 02 §2 is about.
- Dynamic config is a file, not KV. Reason: KV is itself an instance from config; main reads only config.
- The `main` driver: reserved id `main`, one per system, implicit. Runs in a worker with a control channel to main, not inside main. Reason: 01 §2 (main on no request path), 01 §3 (single_thread removed for containment); a broken plugin resolved for `describe` crashes a worker, not main.
- Key `main.dynamicConfig`; `logging:` moves under `main:`. `main.keepRevisions` (default 20).
- D1/D10 Bootstrap: built-in, plain `node:http`, no ws-kit, no auth, own one-form page, one POST that creates the WS API through `main:apply`. `main.bootstrap.enabled`: `off` (default) | `auto` | `always`; not `off` requires `dynamicConfig`. Main only spawns it when not `off`. Bootstrap itself watches `main:config`: a *configured* api with `type: ws` and `main` in `drivers` ⇒ `auto` closes the listener, `always` redirects; POST answers 409. Reason: unauthenticated window only before the first setup. Bootstrap is setup, not lockout insurance.
- D2 Merge kept: static ∪ dynamic by instance id; static instances read-only in the UI; same id in both rejects the dynamic part. `drivers:` is a list and may contain `'*'`. Reason: a static api can then see drivers added dynamically.
- D9 `'*'` = every driver in the merged config except `main`; `main` only by name. Reason: no config writes over e.g. MQTT by a wildcard.
- `'*'` resolution changes links without changing an api's config ⇒ a links-only bucket in the reload plan.
- D3 `apply` returns after validate + file write, before the reload; progress in `config.reload` and `instances`. Reason: an apply relayed by the api being reloaded would deadlock with drain.
- D3/D11 No `http()` on the descriptor. The SPA and bootstrap read api-ws's own config from `main:config`. SPA redirects only when the derived URL changes (`publicUrl`, else bind host/port).
- D4/D14 Backup is an admin procedure (copy files), no export/import methods. Main's write order makes a live copy of the config files consistent: add secrets → dynamic file → revision → drop unreferenced secrets. KV needs a stop or `sqlite3 .backup`.
- Secrets: `sensitive` annotation; values in `/var/lib/evok-node/config.secrets.yaml` (0600) by random ref; read back as `{ $secret: ref }`; ref = keep, plain value = new, omitted = remove; a ref only valid in its own instance.
- D5/D12/D13/D15 Config schema is the same value vocabulary as endpoints (option 4): no zod in the plugin contract. Adds `record`, `checkValue(schema, wire): Issue[]` (generic, runs in the browser too), descriptor `rules?(config): Issue[]`. Limits are binding for config, advisory for endpoints. 08's config becomes a union `source: autogen | manual`. The dynamic file stores no filled-in defaults.
- D6 `helpMd` (Markdown) for long help; `label`, `hint`, `description` stay plain. Module `meta: { label, description?, helpMd?, docsUrl? }`.
- Backup procedure lives in 02a, as an instruction for developers to write the user docs from — not in `docs/user`.
- Tomas commits; agents never commit.
- D16 Values and schemas move to a new chapter 03a.
- D17 Rename `TypedCodec` → `ValueType`, `Codecs` → `Values` (`Codec<T>`, `ValueSchema`, `Infer` stay), as its own commit.
- Readings: `config`, `instances`, `plugins` (grouped by package; install/uninstall later, needs a daemon restart in v1).
