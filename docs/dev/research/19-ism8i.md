# 19 — Wolf ISM8i: protocol and datapoints

**Research, not design.** Facts for the ISM8i driver (12f), for a new TypeScript ISM8i library, and for the central heating driver (12h): the protocol at byte level, connection behaviour, encodings, the datapoint table, writes, and how the BM-2 and mixer modules behave behind it. It supersedes [matter/11 §7](matter/11-thermostat.md), which was written for the thermostat question.

Input from Tomas (2026-10-29):

- Boiler: Wolf **CGB-2-38**. One central **BM-2** on the boiler; no BM-2 in the flats.
- **5 mixer circuits**; ISM8i installed, firmware unknown.
- No ISM8i library exists yet; he wants to write one, as with `mim-b19n` (research/18 §8).
- Which flats are on mixer circuits 1–3, and whether anything is on the direct circuit: not known yet [GAP].

The standalone ISM8i manual (3064356) could not be fetched from any mirror. The facts below come from Wolf's manuals for the same ISM8 module in the KNX set (S15) and the BACnet set (S17), the BAOS protocol description the format follows (S8), and five implementations read in source (S1–S5) [V].

## 1. Frames

The format is the KNX BAOS "ObjectServer" protocol over TCP [V S8]. The ISM8i sends `SetDatapointValue.Req` (`F0 06`); the server acknowledges with `SetDatapointValue.Res` (`F0 86`). A write is `DatapointValue.Ind` (`F0 C1`). "Read all" (`F0 D0`) is not in BAOS — Wolf's own [V S8, V-src S1–S5; I].

### 1.1. Common prefix

| Offset | Bytes | Value | Meaning |
|---|---|---|---|
| 0 | 1 | `06` | header length |
| 1 | 1 | `20` | protocol version 2.0 |
| 2–3 | 2 | `F0 80` | service type: ObjectServer |
| 4–5 | 2 | BE | total frame length, header included |
| 6 | 1 | `04` | connection header length |
| 7–9 | 3 | `00 00 00` | reserved — no channel, no sequence counter |
| 10 | 1 | `F0` | ObjectServer main service |
| 11 | 1 | sub | `06` ISM → server value · `86` server → ISM ACK · `C1` server → ISM write · `D0` server → ISM read all |
| 12–13 | 2 | BE | start datapoint |
| 14–15 | 2 | BE | number of datapoints |
| 16… | | | items |

Each item, from offset `p` (16 first, then `p += 4 + len`) [V-src S1, S4, S5]:

| Offset | Bytes | Meaning |
|---|---|---|
| p | 2 | datapoint ID, BE |
| p+2 | 1 | command/state: `03` from the ISM ("set new value and send on bus" in BAOS), `00` in writes |
| p+3 | 1 | value length — 1 to 4 |
| p+4 | len | value, KNX DPT, BE |

All [V S8, V-src S1, S4, S5]. BAOS v1 packs command and length into one byte; the ISM uses v2's two bytes [V S8, S9].

### 1.2. A value and its ACK

```
ISM → server   DP 372 = 0
06 20 F0 80 00 15 | 04 00 00 00 | F0 06 | 01 74 | 00 01 | 01 74 03 01 00
               len=21            svc     start   n=1     id  cmd len val

server → ISM   ACK — 17 bytes, constant except 12–13 = the frame's start datapoint
06 20 F0 80 00 11 04 00 00 00 F0 86 01 74 00 00 00
                                     start  n=0  error=0
```

[V S7, V-src S1 `ISM_ACK_DP_MSG`, S3, S4, S5]. More captured frames [V S7]:

- keepalive, DP 767: `06 20 f0 80 00 16 04 00 00 00 f0 06 02 ff 00 01 02 ff 03 02 aa bb`
- DP 2 = 11: `06 20 f0 80 00 15 04 00 00 00 f0 06 00 02 00 01 00 02 03 01 0b` [V-src S3]

A frame with two items exists as a test vector (DP 178, 179) [V-src S1]; every frame captured from a device carries one [V S7; I].

### 1.3. Read all

```
06 20 F0 80 00 16 04 00 00 00 F0 D0       — 12 bytes sent, though the length field says 0x16 = 22
```

- All four implementations send exactly these bytes; the issue reporter cites "manual chapter 8.5" [V-src S1, S3, S4, S5; V S6].
- The ISM answered 5 of 6 requests within 0.2–1.9 s and sent everything in about 30 s [V S6]. Wolf: updating all datapoints can take up to 2 min [V S15, S17].
- The length mismatch might make the ISM take the next 10 bytes as part of it — a hypothesis, untested [I, S14].

### 1.4. Write

`prefix | F0 C1 | id | 00 01 | id | 00 | len | value`, length 20 + len, one item [V-src S1 `build_message`, S3, S4, S5]:

```
DP 56  = 50 °C     06 20 f0 80 00 16 04 00 00 00 f0 c1 00 38 00 01 00 38 00 02 14 e2
DP 57  = Standby   06 20 f0 80 00 15 04 00 00 00 f0 c1 00 39 00 01 00 39 00 01 02
DP 65  = −1.5 K    06 20 f0 80 00 16 04 00 00 00 f0 c1 00 41 00 01 00 41 00 02 87 6a
DP 198 = 50 %      06 20 f0 80 00 15 04 00 00 00 f0 c1 00 c6 00 01 00 c6 00 01 80
```

- Generated by running S1's encoder [V-src S1].
- What the ISM answers to a write: [GAP]. BAOS indications are not acknowledged [V S8]; the new value presumably comes back as a `F0 06` [I].
- openHAB always writes the ID's high byte as 0, ioBroker builds it from an unpadded hex string — harmless only because writable IDs are 56–211 [V-src S5, S3; I].

## 2. ACK, order, reassembly

- No sequence counter: bytes 6–9 are `04 00 00 00` in every frame; no implementation checks them [V S7, S8; V-src S1–S5].
- The ACK echoes only the start datapoint, not the items' IDs [V-src S1–S5].
- An unacknowledged telegram is sent again, up to 5 times; five identical frames in one read were captured [V-src S1 test; V S12].

| Implementation | When it ACKs |
|---|---|
| ioBroker | every header-delimited chunk, before parsing [V-src S3] |
| FHEM | `F0 06` frames of 14 bytes or more [V-src S4] |
| wolf_ism8 | not when an item has length 0 or command ≠ `03` — the ISM sends it again [V-src S1] |
| openHAB | only when the frame fills the read chunk; reads ≤ 255 bytes, so a split frame is dropped without ACK [V-src S5] |

- wolf_ism8 keeps no buffer across TCP reads: a frame split across two reads is lost, unacknowledged [V-src S1].
- FHEM drops identical telegrams within one read, losing their order [V-src S4].
- Zero-length items have been seen from a device [V-src S1 test].

## 3. Connection

| Topic | Fact | Tag |
|---|---|---|
| Direction | The ISM8i is a TCP client of one server IP and port (default 12004), set in its web page under Netzwerk → Kommunikationspartner; a change needs a restart | [V S4, S18, S2] |
| Network | DHCP by default, mask /24. Button: 0–1 s eBus detection, 1–5 s temporary IP 192.168.100.68, 5–10 s restart, ≥ 10 s factory reset | [V S17] (BACnet set; [I] same for ISM8i) |
| LEDs | green: off no LAN, blinking data, steady = fault, restart needed · yellow: off no eBus, blinking detecting, steady eBus active | [V S15, S17] |
| After its own restart | sends every datapoint unasked, ~40 s | [V S6] |
| After the server restarts | reconnects, sends nothing ⇒ one read-all needed | [V S6] |
| Read-all right after connecting | "ignored"; the reporter waits 60 s | [V S6] |
| Daily reconnect | firmware 1.90 reconnects about every 24 h | [V S7] |
| Read-all polling | read-all every 5 min caused 112 reconnects in 63 h, 111 of them 5–7 s after a read-all: no answer, SYN from the same port, RST, new connection | [V S6] |
| DP 53 after a reconnect | sends `01`, then `00` ~6 s later | [V S7] |
| Keepalive | DP 767 `aa bb` every 30 s on firmware 1.90; not on 1.60; not in the manuals | [V S7, S6] |
| Push | on change; temperatures only after a change ≥ 0.5 °C; night traffic is sparse | [V S15, S17, S18] |
| Missing values | once DP 58 and 71 stayed missing until the next read-all | [V S6] |
| Modules added later | not detected until the ISM restarts | [V S15, S17] |
| Second server | not possible; one target only. No multicast in any source | [V S4, S2; GAP] |
| BAOS rule | one request at a time; talk at least every 60 s "to prevent a TCP timeout" — a BAOS device's rule, maybe not the ISM's | [V S8; I] |

How implementations handle a silent ISM:

| Implementation | Handling |
|---|---|
| wolf_ism8 / HA | none; read-all only from a button [V-src S1, S2] |
| ioBroker | read-all on accept; optional periodic read-all (default off); no timeout [V-src S3] |
| FHEM | read-all on accept, `SO_KEEPALIVE`, manual reconnect [V-src S4] |
| openHAB | read-all on accept, no timeout [V-src S5] |
| fork in S6 | 120 s watchdog on DP 767 closes the socket; entities unavailable after 60 s more [V S6] |
| one FHEM author | 3600 s silence timeout [V S18] |

Field reports on the "silent ISM" [all forum]:

- Updates stop while the connection looks up; fixed for one user by BM-2 firmware 3.0 [S30].
- Firmware ≤ 1.7: only fault or stale values, power reset every 2–3 months; 1.8/1.81 stable, reaction 1–3 s instead of 5–30 s; "current should be 1.90" [S31, S32].
- Firmware updates are done by Wolf service or the installer, not by the user [S33, S18].

All [V S11, V-src S1, S4, S5].

Where implementations differ:

| Topic | Fact |
|---|---|
| DPT 9 decode | S1/S3/S4 and S5 compute the same value by different formulas [V-src]. wolf_ism8 treats **any** mantissa `0x7FF` as invalid, so `87FF` (−0.01) is lost; only `7FFF` is [V-src S1; I] |
| DPT 9 encode | wolf_ism8 rounds and takes the smallest exponent — correct [V-src S1]. ioBroker uses a fixed exponent 2, no rounding, and overflows above 81.88 (90 → `10 CA` = 8.08) [V-src S3; I computed]. openHAB truncates [V-src S5]. FHEM breaks on negatives [V-src S4] |
| DPT 1.009 | FHEM 0 = open (KNX); ioBroker and openHAB inverted; wolf_ism8 a raw bool [V-src S3–S5; V S5 README]. What Wolf's valve bit means: [GAP] |
| DPT 5.001 | ioBroker decodes `raw × 0.4` but writes the raw percent unscaled [V-src S3] |
| Date, time | weekday ignored or used as day by some [V-src S1, S3, S4] |
| 9.024 kW | values > 1000 dropped (S1) or divided by 1000 (S3) — W-scaled values seem to occur [V-src; I] |
| 13.002 (166, 167) | since firmware 1.9 sometimes unscaled; wolf_ism8 guesses by size [V-src S1] |
| Temperature jumps | wolf_ism8 drops one jump > 20 K ("jumps to zero") [V-src S1] |

## 6. Writes

- Writable, identical in S1, S3, S4: 56–66, 69–79, 82–92, 95–105, 149–162, 193, 194, 198/199, 201/202, 204/205, 207/208, 209, 210; ioBroker adds 211 [V-src].
- "Only datapoints marked Input can be written" [V S15].
- Out-of-range values are ignored without an error; one report of −4.5 K Sollwertkorrektur turning into +4 [V S35, forum 2015].
- Before a write: wolf_ism8 checks R/W, type and range [V-src S1]. ioBroker clamps only the reported value, not the encoded one, and numbers its program UI differently from the wire codes [V-src S3].
- After a write: every implementation updates its own value at once; none waits for a confirmation [V-src S1–S5].
- EEPROM: the MM stores changed parameters "EEPROM permanent", FC81 = EEPROM error [V S21]. No Wolf limit on write frequency found [GAP]. One forum user avoids frequent Sollwertkorrektur writes, fearing BM-2 EEPROM wear — unverified [V S13]. Integrations write on change only; LoxBerry NG drops an unchanged write within 60 s [V-src S20].
- BM-2 parameter A26 "Freigabe Smarthome": forum users say it must be on for ISM writes; its documented default is contradictory [V S24; S33, S34 forum].
- Whether written values survive a power cycle: [GAP].

## 10. Proposals for the library and 12f (not binding)

- **P1 — a library of its own** (`wolf-ism8`, TypeScript, MIT): codec (frame parse/build, DPT 1/5/7/9/10/11/13/20), a datapoint table with firmware per ID, and a server session. Transport-free like `mim-b19n` should be: it takes a duplex byte stream, so 12f owns the socket.
- **P2 — stream reassembly.** A buffer across reads, frames cut by their length field; ACK every complete `F0 06` frame at once, even one whose items don't decode — log those instead of letting the ISM resend.
- **P3 — DPT 9 by wolf_ism8's encoder;** only `7FFF` invalid. 1.009 exposed as the raw bit.
- **P4 — liveness.** No periodic read-all (it triggered resets). One read-all ~60 s after a new connection when nothing has arrived. Watchdog on DP 767 (≥ 120 s silent ⇒ close the socket) once 767 has been seen; without 767, a long silence timeout (S18 uses 3600 s) and no forced close.
- **P5 — one connection.** A second connection replaces the first.
- **P6 — writes on change only, rate-limited** (e.g. one per datapoint per 60 s, as LoxBerry NG), range-checked by the table; no optimistic value — the reading follows what the ISM sends back.
- **P7 — debounce DP 53** after a reconnect (`01` then `00`).
- **P8 — firmware** read from the web page once, for the table; unknown ⇒ the 1.9 table.
- **P9 — for 12h.** Mixer circuits 1–3: Sollwertkorrektur, program, flow, pump. Mixer circuits 4–5: nothing through the ISM — run by the BM-2 alone, valves only. With no BM-2 in the flats, ISM room temperature is empty.
