# 02 — Main: configuration and runner

## 1. Scope

This file is `main`'s whole job: how the config — one static file, optionally merged with a dynamic one (§3a) — becomes a running, live set of driver and api instances, and how that set changes without a restart. It states the runner (01 §4) concretely, and the parse and reload machinery that spawns and replaces instances through it; how a `type` is found — plugins and their manifest — is 02b. It does not state: the envelope a running instance actually speaks (03), the shared runtime a module may lean on (04), what a driver or api must guarantee on its own terms (05, 13), how user data is actually stored (06), how a hardware definition is shaped (07), or how a specific driver's own config dict interprets `autogen` (08, 09, 10) — `main` never sees those keys, so this file cannot describe them either. The `main` driver, which reads and writes the dynamic part for a UI, and the bootstrap api are 02a's.

## 2. The four kinds of data

Four kinds of data exist, and this file is only about the first. **Config** — operator intent: buses, ports, scan rates, which apis run — is written by an operator: by hand in `/etc/kapsle/config.yaml`, or through the `main` driver (02a) into the dynamic file (§3a). The daemon never writes it on its own. The other three are someone else's: **user data** (aliases, groups, labels, plugin settings), written by users through an api at runtime and held by the KV-store driver (06); **platform facts** (our hardware definitions, our generated inventory), shipped or generated by our own package and never written by a human or the daemon; and **readings** (current values, health, counters), produced by a driver's scan loop and never persisted at all (05).

The distinction is not academic — conflating the first two is exactly where EVOK's alias handling failed. What matters for this file: config is the only one of the four `main` is allowed to read, and the only one whose shape this file describes. A UI writing config does not turn user data into config: home devices, rules and their settings stay in KV (06).

## 3. Config structure

Global config is small: which drivers and apis exist, plus main's own operational settings, and nothing else — no defaults that quietly change a *module's* behaviour out from under it. Everything a specific instance needs is that instance's own slice, opaque to `main` and to every other instance.

The one property at this level that is not a driver or an api is `main:` — main's own settings: `logging` ([04 §3](04-Common-services.md#3-logging)), `dynamicConfig` and `keepRevisions` (§3a), `plugins` — `registry`, `locked`, `packages` (02b §9.3, §9.5), `bootstrap` (02a). It is optional, and only the static file holds it; absent, `main` logs to stdout/journald only, at `info`, and runs on the static file alone.

`drivers:` and `apis:` are maps keyed by id. The key is the instance's **identity** — the thing reload compares old and new config on (§5). An id is not a device address and not a display name; renaming one is deletion plus creation, not a rename, and anything keyed on that id (its KV namespace, 06 §2) goes with it. `main` and `bootstrap` are reserved (02a): an entry with either as its id or its `type` is a configuration error. `kv` is reserved too, but as an optional entry (§3b).

Every instance, driver or api, carries one property `main` itself understands beyond its id: `run`, the placement (01 §3) — `worker_thread` or `child_process`, defaulting to `worker_thread`. An api carries one more: `drivers`, the driver ids it links to (03 §8) — standardized at this level because 01 §9 states it as a rule for every api, not a per-api convention. `drivers` is a list; `'*'` in it stands for every driver in the merged config except `main`, which is linked only by name (03 §8). A driver's equivalent is never a generic key here; it comes from that driver's own descriptor (§4, 03 §8), because what it needs to say alongside a peer's id is the driver's own business. Everything else under an instance's key is that module's own schema, validated by that module's own rules (§5), never `main`'s.

```yaml
# /etc/kapsle/config.yaml
main:
  logging: { level: info }      # 04 §3

drivers:
  PLC:
    type: onboard
    run: worker_thread          # default; shown for clarity
    # ... the rest is driver-onboard's own schema

  EXT:
    type: extension
    run: child_process
    # ... driver-extension's own schema

apis:
  ws:
    type: ws
    drivers: ['*', main]        # every driver, and the main driver by name — 03 §8
    # ... api-ws's own schema
```

`type` names a `driver` or `api` plugin (§4, 02b); it is the one key every instance has beyond its id, `run`, and its own schema.

## 3a. Static and dynamic config

With `main.dynamicConfig: true`, config comes from two files:

```yaml
# /etc/kapsle/config.yaml — written by hand
main:
  dynamicConfig: true
  keepRevisions: 20                  # default 20 — 02a
  bootstrap: { enabled: auto, listen: { port: 8088 } }   # 02a — stays closed here: `ws` already links `main`
drivers:
  kv: { type: kv-store }
apis:
  ws: { type: ws, drivers: ['*', main] }
```

```yaml
# /var/lib/kapsle/config.dynamic.yaml — written only by main, when the main driver applies a change (02a §3.1)
revision: 42
drivers:
  PLC: { type: onboard, source: autogen }
apis:
  mqtt: { type: mqtt, drivers: [PLC] }
```

- **Merged by instance id**, `drivers:` and `apis:` each: the merged config is the static entries plus the dynamic ones. No deep merge, no override — an entry is whole in one file.
- **Static entries are read-only** through the `main` driver: only the file changes them.
- **An id in both files** is an issue on the dynamic entry (§5).
- **Links cross files.** A static entry may name a dynamic driver; removing that driver then fails validation. `'*'` never blocks a removal.
- **Only the static file holds `main:`.** The dynamic file holds `revision`, `drivers:` and `apis:`, nothing else.
- **`dynamicConfig` absent or `false`** ⇒ the static file alone, exactly as without this section. The `main` driver still runs, read-only (02a).

The dynamic file's own rules — revisions, secrets, write order, where the files live — are 02a's.

## 3b. The `kv` driver

`kv` is the one authoritative KV store (06). Every other instance links to it without naming it.

```yaml
drivers:
  kv:                          # optional; absent ⇒ main adds kv: { type: kv-store }
    type: kv-store             # any other type ⇒ configuration error
    run: child_process         # replaces the default, as in any entry
    path: /data/kv.db          # optional for kv — 06 §5
  archive:                     # another kv-store is allowed
    type: kv-store
    path: /data/archive.db     # required for any id but kv
```

- **Reserved id, optional entry.** Absent ⇒ `main` adds `kv: { type: kv-store }` to the merged config, so the defaults apply. Present ⇒ its `run` and body replace them.
- **Static file only.** A `kv` entry in the dynamic file is an issue on it and is left out (§5); `kv` keeps the static entry or the defaults. The store never moves because an apply went wrong.
- **Linked from every instance.** Every driver and api — the `main` driver and the bootstrap api too (02a) — gets a link to `kv`; `kv` itself links nothing. It is an ordinary link and shows in `links()`/`onLink` (03 §4). Naming `kv` in `drivers:` or `declaredLinks` as well is the same link, once.
- **Configured first** at startup (§5 step 6), so a consumer reading KV in its `configure` is not answered `not-ready`.
- **Reload as any entry** (§5.1): `kv` changes only when its own entry does (06 §8). Removing the entry changes it back to the defaults; it is never a removal. No other instance is relinked.
- **Linked is not exposed.** What an api shows its clients is the api's decision (13 §6).

## 4. Module definition

**A module is two exports:** a `ModuleDescriptor`, and the `ModuleInstance` type it produces. Neither belongs to `main`'s source — `main` only ever sees them after resolving a `type` through the plugin manifest (02b): kind `driver` for an entry under `drivers:`, kind `api` for one under `apis:`.

A module's config travels as its **body**: plain, JSON-shaped data — strings, numbers, booleans, null, arrays, plain objects, nothing else — because it comes from YAML, whose value model is exactly JSON's. `Config` is that body decoded through the module's own `ValueType` (03a, §5), so it may hold what decode makes of it — a `bigint`, a `Date`, bytes. Only the body crosses to an instance; the instance's side decodes it again with the same descriptor (§6).

```ts
// One instance's own config — illustrative. Plain data throughout; the TS type is inferred.
const ExampleConfig = Values.struct({
  transport: Values.struct({
    host: Values.string({ label: 'Host' }),
    port: Values.uint16({ label: 'Port', min: 1, default: 502 }),
  }),
  scanMs: Values.uint32({ label: 'Scan period', unit: 'ms', min: 10, default: 100 }),
});
type ExampleConfig = Infer<typeof ExampleConfig>;   // { transport: { host: string; port: number }; scanMs: number }
```

```ts
// Pure data and pure functions — safe to load into main's own process without spawning anything.
// Configurable — meta, config, rules, declaredLinks — is 02b §5.1.
interface ModuleDescriptor<Config> extends Configurable<Config> {
  isConfigEqual(prev: Config, next: Config): boolean;
  createInstance(ctx: InstanceContext): ModuleInstance<Config>;
}

// What the runner (§6) hosts on the instance's own side, wherever that is. Identical
// shape under worker_thread and child_process (01 §3).
interface ModuleInstance<Config> {
  configure(config: Config): Promise<void>;   // async init a constructor can't do — createInstance is synchronous
  start(): Promise<void>;
  drain(): Promise<void>;
  stop(): Promise<void>;
  reload?(config: Config): Promise<void>;              // absent ⇒ the runner stops it instead (§6)
  prepareReload?(nextConfig: Config): Promise<void>;    // releases what nextConfig won't need;
                                                         // sibling to reload, not a replacement — a
                                                         // module with nothing shareable to give up
                                                         // can implement reload alone (§6)
}
```

`InstanceContext` is what the runner hands every instance regardless of placement — its messaging handle (03) and whatever common services (04) it asked for. Its shape is 03's to define, not this file's.

**`ModuleDescriptor`, `ModuleInstance` and `InstanceContext` — together with the messaging contract a module speaks through it (03) and the plugin contract (02b) — are published as `@kapsle/module-sdk`**, along with the guard below. There is no separate `messaging` package: the wire types have the same audience as the module contract, and `module-sdk`, unlike `main`, is actually published — the second package this project publishes, after `client`. A plugin author writes against the real contract, messaging included, and can run the exact check `main` runs, in their own tests, before shipping.

The guard of the `driver` and `api` kinds (02b §5.2), both owned by `module-sdk`:

```ts
// Duck-typed, not `instanceof` — 02b §5.1.
function isModuleDescriptor(x: unknown): x is ModuleDescriptor<unknown> {
  return (
    typeof x === 'object' && x !== null &&
    (x as { meta?: { label?: unknown } }).meta?.label !== undefined &&
    typeof (x as { config?: { codec?: { decode?: unknown } } }).config?.codec?.decode === 'function' &&
    typeof (x as { config?: { schema?: unknown } }).config?.schema === 'object' &&
    typeof (x as { isConfigEqual?: unknown }).isConfigEqual === 'function' &&
    typeof (x as { createInstance?: unknown }).createInstance === 'function'
  );
}

const driverKind: KindDefinition<ModuleDescriptor<unknown>> = {
  kind: 'driver', meta: { label: 'Driver' }, target: 'node',
  guard(mod, id) {
    if (!isModuleDescriptor(mod)) throw new Error(`driver "${id}": not a valid ModuleDescriptor`);
    return mod;
  },
};
// apiKind: the same, kind 'api'
```

A module has no id of its own: its `type` is the manifest's `id`.

## 5. `main`: startup, config and reload

Startup is one sequence, run once, in order:

1. **Assemble the plugin manifest** (02b §6.1) — built-ins and plugins alike, one mechanism. Before it, a staged plugin generation becomes current (02b §9.2).
2. **Read** `/etc/kapsle/config.yaml` — with `main.dynamicConfig`, also the dynamic file and the secrets file (02a). A missing dynamic file is an empty one.
3. **Check the skeleton** — `main`'s own value types, checked binding (03a §5.1). The top level holds `main:`, `drivers:` and `apis:` only; `drivers:`/`apis:` are maps keyed by id. Each entry splits into its **head** — `type`, `run` and, for an api, `drivers` — and its **body**, everything else. Only the head is `main`'s; the body is the module's (step 4). `main.bootstrap` splits the same way: `enabled` is `main`'s, the rest is api-bootstrap's (02a).

   ```ts
   const ID = '^[A-Za-z0-9_-]+$';                    // every key under drivers:/apis: — 'main' and 'bootstrap' are reserved (02a)

   const InstanceHead = Values.struct({
     type: Values.string(),
     run: Values.string({ enumValues: ['worker_thread', 'child_process'], default: 'worker_thread' }),
     drivers: Values.optional(Values.array(Values.string({ pattern: '^([A-Za-z0-9_-]+|\\*)$' }))),   // apis only; '*' — 03 §8
   });

   const LoggingConfig = Values.struct({
     level: Values.string({ enumValues: ['trace', 'debug', 'info', 'warn', 'error', 'fatal'], default: 'info' }),
     file: Values.optional(Values.string()),
     pretty: Values.bool({ default: false }),
   });   // absent ⇒ stdout/journald only, level info (04 §3.3.1)

   const MainConfig = Values.struct({
     logging: Values.optional(LoggingConfig),
     dynamicConfig: Values.bool({ default: false }),
     keepRevisions: Values.uint16({ min: 1, default: 20 }),
     plugins: Values.struct({
       registry: Values.string({ default: 'https://registry.npmjs.org' }),   // 02b §9.3
       locked: Values.bool({ default: false }),                             // 02b §9.5
       packages: Values.optional(Values.record(Values.string())),           // name → npm spec — 02b §9.5; needs locked
     }),
     bootstrap: Values.optional(Values.struct({
       enabled: Values.string({ enumValues: ['off', 'auto', 'always'], default: 'off' }),
     })),   // head only — the rest is api-bootstrap's (02a)
   });
   ```

4. **Per instance, resolve and check.** Resolve `type` through the `PluginRegistry` (02b §6.2) — under `kind: 'driver'` for an entry from `drivers:`, `kind: 'api'` for one from `apis:` — to a `ModuleDescriptor`; check the body against its `config`, decode it, then run its `rules`:

   ```ts
   const { type, run, drivers, ...body } = rawInstance;
   const module = await registry.resolve<ModuleDescriptor<unknown>>(isApi ? 'api' : 'driver', type);   // no entry, load failure, or bad shape
   const issues = checkValue(module.config.schema, body, { limits: 'binding' });            // 03a §5
   issues.push(...await checkNested(module.config.schema, body, registry));                 // every Values.plugin in the body — 02b §8
   const config = module.config.codec.decode(body);                                           // only when issues is empty
   issues.push(...(module.rules?.(config) ?? []));
   ```

   Two value types, each owning exactly its own keys — the head `main`'s, the body the module's — never one merged one. `main` never sees what is inside `body` beyond its issues. In a dynamic entry, a `sensitive` member holds a secret ref; `main` puts the stored value in its place before this step (02a). For a driver, its declared links come from that parsed `config` itself — `module.declaredLinks?.(config)` (03 §8) — never from a key `main` reads directly, the way an api's `drivers` list already was; a nested plugin's `declaredLinks` join them (02b §8). Two checks are `main`'s, because a module's `rules` never sees its id (§3b): an entry `kv` with a `type` other than `kv-store`, and a `kv-store` under another id without `path`.

5. **Resolve cross-instance concerns** no single module can see on its own (§7) — merging the two files (§3a), where an id in both is an issue on the dynamic entry; expanding every api's `'*'` (03 §8); adding the `kv` default and its implicit links (§3b); assembling the full `instanceId → DriverId[]` link topology from every api's `drivers` and every driver's `declaredLinks`, and validating it (03 §8): every referenced id exists in `drivers:` or is `main` (02a), and a cycle is fatal.
6. **Spawn, configure, start — three passes, not one.** For every instance: `runnerFactory.spawn(module, id, type, run, links, manifest)` — `manifest` is the whole plugin manifest from step 1, identical for every instance (02b §6.1, §6). Once every instance is spawned: `runner.configure(config)` for every instance, awaiting all of them. Only once every instance is configured: `runner.start()` for every instance (§6, 03 §9). The `main` driver is always one of them, and the bootstrap api one more when `main.bootstrap.enabled` is not `off`; neither is an entry in either file (02a). `kv` is always one too (§3b), and its `configure` resolves before any other instance's begins.

Every failure from step 1 through 5 in a built-in package or the static file is fatal at startup — a built-in package's bad manifest (02b §7), a config file that does not parse, a `type` with no plugin, an instance body that fails its own module's value type or rules. None of these degrade; the daemon does not start on any of them. Both mean "this cannot possibly run," never "this runs in a reduced way." A plugin package's own problem only drops that package (02b §7); a static entry that used it then fails as a `type` with no plugin.

**The dynamic file is the one exception, and it degrades per entry.** It was valid when the `main` driver wrote it; what makes it fail at startup is the world changing under it — a plugin upgraded with a new schema, a plugin removed. Failing the daemon for that would also take down the UI that has to fix it.

| Fails at startup | Result |
|---|---|
| the dynamic file does not parse | every dynamic entry is left out |
| a dynamic entry: unknown `type`, an issue in its body or rules, an id the static file also has, a link to an id in neither file, a cycle | that entry is left out |
| a dynamic entry linking to a left-out driver | starts; the link stays down (03 §10), as if that driver had crashed |
| a static entry linking to a driver the dynamic part does not deliver — file missing, not parsing, or that driver left out | fatal: a static-file error, as above |

A left-out entry stays in its file, and `main:config` shows it with its issues (02a §2.3); it is only not spawned. Leaving one out never leaves another out. A reload that finds it valid adds it like a new entry; one that does not touch it leaves it out (§5.1).

`kapsle config check` (basics/01 §3.2.1) runs steps 1 through 5 read-only — no generation swap, nothing spawned — and prints the issues.

### 5.1. Reload

**Reload repeats steps 2 through 5 against the files as they are now.** It is triggered by `systemctl reload` (basics/01 §3.2), or by an apply through the `main` driver, right after `main` wrote the dynamic file (02a §3.1). A failure anywhere in those steps — a file no longer parses, an instance's body no longer fits its module's schema — rejects the reload outright: a caught, handled decision, not a thrown exception that could take `main` down. Every running instance is left exactly as it was; reload either replaces the whole config or changes nothing, never partially. **One exception: an entry already left out (§5) and not changed by this reload stays left out** and does not reject it; every entry the reload adds or changes must be valid.

Once steps 2 through 5 succeed, the new config **is** current — from here on `main` compares against it, whatever happens next to any individual instance. Applying it to the running instances is two rounds, not one, run as a barrier: every id's prepare completes before any id's commit begins. This is what keeps two drivers exchanging a shared transport safe — whichever one is giving it up has released it in prepare, before the one gaining it can acquire anything in commit, and `main` never has to know the two are related to get that ordering right.

**Prepare**, for every id:

- **absent from the new config** (removed) → `runner.stop()`. Its resources are gone; nothing about it survives into commit.
- **present in both, `isConfigEqual` true, same resolved links** → untouched. Not part of this reload at all.
- **present in both, `isConfigEqual` true, resolved links changed** (links-only: an api with `'*'`, a driver added or removed) → `runner.relink(links, 'prepare')` closes the links no longer needed; the instance itself is untouched.
- **present in both, `isConfigEqual` false** → `runner.prepareReload(newConfig)` (§6). What that actually does is the runner's decision, not `main`'s: call the instance's own `prepareReload` if it has one, do nothing yet if it only has `reload`, or stop it outright if it has neither — three different outcomes behind one call.
- **absent from the old config** (added) → untouched here; it has nothing to release yet.

**Commit**, only once every prepare above has resolved, for every id:

- **added** → `runnerFactory.spawn` then `runner.configure(newConfig)` and `runner.start()`.
- **changed** → `runner.commitReload(newConfig)` (§6): reloads the instance in place if it survived prepare, or constructs and starts a fresh one if prepare stopped it.
- **links-only** → `runner.relink(links, 'commit')` opens the new links; the instance learns of both through `onLink` (03 §4), with no `reload`.
- **removed or unchanged** → nothing further.

Link topology is diffed alongside config, for the same ids: `prepareReload` also closes whatever the new topology no longer needs for that id — the same "releases what nextConfig won't need" job it already has for anything else a module gives up (03 §9) — and `commitReload` opens whatever it newly needs, before calling the module's own `reload`. §8.5's `computeReloadPlan` grows the matching diff: for a changed id, old `declaredLinks`/`drivers` against new — empty whenever `isConfigEqual` is true for a declared list, since both are pure functions of `Config`. `'*'` is the exception: it follows the set of drivers, which is what the links-only bucket is for.

**`main:` on reload.** `logging`, `keepRevisions`, `plugins.registry` and `plugins.locked` take effect at once; a changed `plugins.packages` changes nothing until `plugins sync` and a restart (02b §9.5). `bootstrap` is in the plan like an instance: added, removed or changed with `main.bootstrap`. A changed `dynamicConfig` takes effect only at the next daemon restart; until then `main:config` carries an issue saying so (02a §2.4).

A `start()` that rejects during commit — the config was valid, but the instance still could not come up — is accepted, not retried: `main` logs it and moves on to every other id in the batch. That instance is simply not running, current config or not, until the next reload or an explicit restart gives `start()` another chance. Being graceful under `start()` is the module's own responsibility; `main` does not compensate for it, the same way it does not retry a driver's own "device unreachable."

Reload granularity is therefore never a global policy — it is whatever `prepareReload`/`commitReload` resolve to for one instance, and `main`'s own logic does not need to know why. Nothing here promises an order between independent instances beyond the one barrier above: two changed ids commit in no particular order relative to each other, only ever after, never before, every prepare is done.

## 6. The runner

`main` holds a `Runner` per running instance, and calls only this — never a `ModuleInstance` directly. That is the whole point: placement is invisible on `main`'s side of this interface.

```ts
type Placement = 'worker_thread' | 'child_process';

interface Runner<Config> {
  readonly id: string;
  readonly placement: Placement;

  configure(config: Config): Promise<void>;   // createInstance(ctx) → instance.configure(config)
  start(): Promise<void>;                     // instance.start()
  // Prepare/commit are §5's barrier. What each one actually does — call the instance's
  // own hook, do nothing yet, or stop/restart outright — is this runner's decision alone;
  // main only ever makes these two calls, never a branch on what the instance supports.
  prepareReload(config: Config): Promise<void>;
  commitReload(config: Config): Promise<void>;
  // Links-only (§5.1): 'prepare' closes what `links` no longer holds, 'commit' opens what is new.
  relink(links: readonly DriverId[], phase: 'prepare' | 'commit'): Promise<void>;
  stop(): Promise<void>;
}

interface RunnerFactory {
  spawn<Config>(
    descriptor: ModuleDescriptor<Config>,
    id: string,
    type: string,            // the instance's `type` — 03 §9's InstanceContext surfaces it as driverTypeName
    placement: Placement,
    links: readonly DriverId[],                                   // 03 §8 — resolved before spawn, never after
    manifest: Manifest,      // 02b §6.1 — the whole plugin manifest; every instance gets it, not just what its own type needs
  ): Runner<Config>;
}
```

What `spawn` actually does is the one place placement matters — and now that only two placements exist, both share one description with a single difference at the bottom. `config` reaches an instance only through `configure`, never through `spawn` — `createInstance` takes just `ctx` (02 §4), so `ctx` (including its messaging handle, wired from `links`, and the plugin manifest above) has to exist before construction, not after.

`spawn` starts the hosting environment — a `worker_threads.Worker` for `worker_thread`, a forked process for `child_process` — running a small bootstrap, code living in `main`'s own package, never the module's, and attaches an `'error'`/`'exit'` listener to it (03 §11 — this is how `main` finds out about a crash it didn't ask for). The bootstrap receives `{ kind, type, id, links, manifest }` over `postMessage` (worker) or the fork's IPC channel (child process) — the module still a manifest entry, not yet resolved — resolves `(kind, type)` to its `ModuleDescriptor` through its own `PluginRegistry` (02b §6.2, the same mechanism, running inside the worker/child, built from `manifest`), wires its own `ctx` — including `ctx.plugins`, that same `PluginRegistry` (03 §9) — from `links` and `manifest` (binding whatever socket 03 §10 says it needs), and constructs the `ModuleInstance` there. Every subsequent `Runner` method sends a message and awaits the matching reply; The checked body and the lifecycle results cross as plain data (§4), first at `configure`, never at `spawn`; the bootstrap decodes the body to `Config` before calling the instance. Only the underlying transport differs between the two — `postMessage` versus the fork's IPC — the bootstrap and resolution step are otherwise identical.

`main` sequences every instance's `configure` before any instance's `start` (§5, 03 §9) — the runner itself no longer chains the two, that ordering is main's own barrier now. `stop()` sequences `instance.drain()` → `instance.stop()`: drain tells the instance to stop taking on new work so anything in flight can finish, then stop releases the underlying resources. This sequencing happens inside the bootstrap, not as separate round-trips.

The runner tracks its own state per instance (not-started / running / stopping / stopped / failed), which is what makes `start()` and `stop()` idempotent: a second `stop()` on an already-stopped or stopping runner resolves without calling `instance.stop()` again; `start()` while already running is a no-op. A `configure()` or `start()` that rejects leaves the instance and its underlying thread/process exactly as they are — the runner neither stops nor discards them — so a later retry or an explicit `stop()` can still be issued against the same instance. Whether the instance is actually safe to retry from a partially-completed lifecycle is the module's own responsibility (§5).

A `Runner`'s calls to its instance, and everything the instance sends onward to other drivers or apis once running, all travel as the same kind of envelope, whatever carries it underneath — an in-process call, `postMessage`, IPC. What that envelope actually contains — a request, a response, an event — is 03's; this file only needs that a `Runner`'s methods cross *some* channel, and that the channel is opaque to `main`.

The `main` driver's runner carries one channel more, to `main` itself (02a). It is the only instance with one.

## 7. Resource reservation

`main` does not enforce resource exclusivity — two drivers naming the same serial port, the same TCP host and port, two `kv-store` instances on the same `path`, are not `main`'s problem to solve. It is the developer's and the administrator's responsibility not to configure a collision, and 01 §7's whole point is that the common case (several drivers wanting one bus) has a correct answer that does not need policing: share it through a transport driver rather than opening it twice.

What `main` does do: at parse time, warn on a detectable collision — same port, same host:port, same `kv-store` `path` — so a mistake surfaces immediately instead of as a runtime failure days later. A warning is not a gate; an administrator who wants two drivers on one port anyway gets to have it.

## 8. Testing

Tier 1 (unit) only, scoped to `main`'s own package — no simulator, no hardware, no other module's code. See [`design/basics/03-Testing.md`](../basics/03-Testing.md) for the tiers.

### 8.1. Fixture modules

Backing every test below that needs a real, resolvable module: fixture "packages" under `packages/main/tests/fixtures/modules/`, each shaped exactly like a real plugin package (02b §3) — `package.json` with a `kapsle` block, `dist/index.js` exporting a `ModuleDescriptor` as default. Assembly, namespaces, status and laziness are tested in 02b §11; this file tests what `main` does with the result.

- `module-ok/` — a valid descriptor. Its `config` value type carries at least one required field and one defaulted field, and its `rules` one rule, reused by §8.4's config-parse tests. `createInstance` returns a fully controllable mock instance (§8.2).
- `module-load-fails/` — `dist/index.js` throws on import.
- `module-bad-shape/` — imports fine, but the export fails `isModuleDescriptor`.
- `module-nested/` — a descriptor whose config holds a `Values.plugin` of a fixture nestable kind, with a fixture plugin of that kind that declares links.

### 8.2. The mock instance

`module-ok`'s `configure` takes config knobs a test can set: `failAt: 'configure' | 'start' | null`, `delayMs`, and a path to append lifecycle events to — the only way to observe call order across a `worker_thread`/`child_process` boundary. `createInstance` itself takes no config (§4) and is never given anything to fail on.

Manifest-root injection: `assembleManifest(rootDir?)` takes the fixture directory directly instead of real `node_modules`. For `worker_thread`/`child_process`, `rootDir` rides along in the same `{ kind, type, id, links, manifest }` message the bootstrap already receives (§6) — no environment variable needed.

### 8.3. Module loading

- `resolve('driver', type)` succeeds for `module-ok`; rejects for an unknown type, `module-load-fails`, and `module-bad-shape` — in a static entry each is fatal at startup, in a dynamic one the entry is left out.
- `isModuleDescriptor` rejects an export without `meta.label`, without `config.codec.decode`, or without `config.schema`.
- `module-nested`: a bad nested `config` is an issue at `[<ref path>, 'config', …]`; the nested plugin's `declaredLinks` are in the instance's links.
- A staged `next` generation becomes `current` before assembly (02b §9.2).
- `config check`: with a staged `next`, a type only `next` has passes; `next` stays staged and nothing is spawned; an issue exits 1.

### 8.4. Config parse and validate

Fixtures under `packages/main/tests/fixtures/config/*.yaml`, one issue per file, each targeting one step of §5: `valid.yaml`; `invalid-yaml.yaml`; `bad-skeleton-*.yaml` (bad id / missing `type` / bad `run`); `unknown-type.yaml`; `module-body-invalid.yaml` (body fails `module-ok`'s own value type); `module-rule-fails.yaml` (`module-ok`'s rule); `reserved-id.yaml` (`main`, `bootstrap`); `kv-wrong-type.yaml`; `kv-store-no-path.yaml` (a `kv-store` under another id); `unknown-top-level.yaml`. Every fixture's test asserts the specific cause, even though §5 treats all of them as one failure class.

Static and dynamic, each a pair of files (§3a): `dynamic-valid` (merged as expected); `dynamic-unparsable` (static instances start, every dynamic one is left out); `dynamic-entry-invalid` (only that entry is left out, the rest start); `dynamic-id-collision` (the dynamic entry is left out, the static one starts); `dynamic-link-to-left-out` (the linking entry starts with that link down); `star-links` (`'*'` expands to every driver but `main`; `main` only by name); `dynamic-off` (the dynamic file is never read); `static-links-dynamic` (a static link to a driver the dynamic part does not deliver is fatal); `dynamic-kv` (left out; `kv` keeps the static entry or the defaults).

`kv` (§3b): absent ⇒ added with the defaults; present ⇒ its body; every instance but `kv` links it, once even when it also names it; `kv` is configured before any other instance.

### 8.5. Config equality and the reload plan

Worth naming §5.1's removed/unchanged/changed/links-only/added logic as its own pure function — `computeReloadPlan(oldConfig, newConfig, registry)` — testable with no `Runner` involved. One test per bucket — links-only by adding a driver under an api with `'*'` — using `module-ok`'s `isConfigEqual` driven by a `marker` field.

### 8.6. The runner

Against `module-ok`, in both placements:

- `spawn` constructs the instance via a real `Worker`/child (assert a pid/threadId, or that non-cloneable data fails to cross, as proof it's genuinely out-of-process — both placements guarantee this now, with no in-process case left to compare against).
- `configure()` then `start()` are two separate calls now (§6); graceful and errored runs (mock rejecting at either step) are each asserted via the lifecycle log / the rejection surfacing through the matching call.
- `stop()` sequences `drain → stop`; assert the underlying thread/process actually exits.
- Idempotency: a second `stop()` doesn't re-invoke `instance.stop()`; `start()` while running is a no-op — assert via the mock's own call count.
- Cleanup after a failed `start()`: the thread/process is still alive, and a retried `start()` completes against the same instance, not a re-spawn.

### 8.7. Reload

Using a spy `RunnerFactory` — no real threads; real placement is already covered by §8.6:

- The barrier: delay one id's prepare, assert no commit fires before it resolves.
- An instance stopped in prepare is freshly spawned in commit.
- A config failing parse/schema touches zero runners.
- A links-only instance never sees `prepareReload`/`reload`; its `onLink` fires for each link closed and opened.
- A left-out entry the reload does not change stays left out and does not reject it; a changed entry that is invalid rejects the whole reload.
- `main.bootstrap` changed: bootstrap is added, removed or reloaded; `dynamicConfig` changed: nothing moves, `main:config` carries `restart-needed`.
- One id's `start()` failing during commit doesn't affect siblings or reject the reload as a whole.
